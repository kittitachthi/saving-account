# ADR-012: Pocka Marketing Entry และ Beta Waitlist

## สถานะ

ยอมรับ

## บริบท

หน้าเริ่มต้นสำหรับผู้ใช้ที่ยังไม่มี Session แสดงเพียงกล่องเข้าสู่ระบบ ทำให้ผู้ใช้ใหม่ยังไม่เข้าใจว่าแอปช่วยอะไร ขณะเดียวกันระบบยังเป็น Private Beta และอนุญาตให้สร้างบัญชีเฉพาะ verified Google email ที่อยู่ใน Beta Allowlist เท่านั้น จึงไม่ควรสื่อว่าบุคคลทั่วไปสมัครและเริ่มใช้งานได้ทันที

ผลิตภัณฑ์จะใช้ชื่อ **Pocka (พ็อกก้า)** ซึ่งเชื่อมโยงกับคำว่า pocket และวางตำแหน่งเป็นเว็บแอปจัดการเงินส่วนบุคคลที่เรียบง่ายสำหรับคนทั่วไป จุดสัญญาหลักคือช่วยให้ผู้ใช้รู้ว่าเงินหายไปไหน โดยไม่ต้องมีความรู้บัญชี

## การตัดสินใจ

- เปลี่ยน anonymous entry จาก Login card เป็น Marketing Landing Page ภาษาไทยแบบกระชับ 3–4 ช่วง และยังคงไม่แสดงข้อมูลการเงินจริง
- ใช้ข้อความหลัก “เงินหายไปไหน ให้ Pocka ช่วยหา” และข้อความรอง “จดง่าย เห็นชัด ว่าเงินไปไหน พร้อมแยกเงินเก็บและดูภาพรวมในที่เดียว”
- จุดขายหลักคือการจดรายรับ–รายจ่ายที่ง่าย การเห็นเงินพร้อมใช้จริง การแยกเงินเก็บ และการดูภาพรวมผ่านกราฟ
- การแชร์กระเป๋าแบบอ่านอย่างเดียวเป็นความสามารถรอง ไม่ใช้เป็นแกนหลักของ Hero
- ใช้ภาพจำลองที่อิง UI จริงกับข้อมูลสมมติเท่านั้น ห้ามใช้ข้อมูลการเงินจริงใน Marketing Page
- Brand ใช้สีเขียว รูปทรงมน และมาสคอตกระเป๋าใส่เหรียญทรงกลม เพื่อให้สดใส เป็นมิตร และทำให้การจดเงินไม่น่าเบื่อ โดยยังรักษาความน่าเชื่อถือของผลิตภัณฑ์การเงิน
- ออกแบบ Web/Desktop เป็นหลักและรองรับ Responsive Web ตั้งแต่ 320px ขึ้นไป ห้ามเรียกผลิตภัณฑ์ว่า Native App หรือใช้ข้อความ “ดาวน์โหลดแอป”
- Marketing Page ใช้ theme preference ชุดเดียวกับ protected application แสดง Theme Switch บน navigation และเลือกค่าที่ผู้ใช้บันทึกไว้ก่อนค่าเริ่มต้นของระบบ
- CTA หลักคือ “ขอเข้าร่วม Beta” ซึ่งเลื่อนไปยังฟอร์มท้ายหน้า CTA รองคือ “เข้าสู่ระบบ” บน navigation
- ปุ่มเข้าสู่ระบบเปิด Dialog บนหน้าเดิมและเสนอ “เข้าสู่ระบบด้วย Google” สำหรับผู้ได้รับเชิญ ข้อความนี้เป็นคำมาตรฐานทุกจุดของ Authentication UI และต้องไม่ใช้แทน CTA ขอเข้าร่วม Beta
- ปุ่ม “เข้าสู่ระบบด้วย Google” ใช้ Google “G” แบบสีมาตรฐานและ Light หรือ Dark treatment ตาม Sign in with Google Branding Guidelines ห้ามย้อมโลโก้หรือพื้นปุ่มเป็นสีเขียวของ Pocka
- คง server-side Authorization Code/OIDC redirect flow เดิมไว้ และ render ปุ่มเป็น HTML/CSS ด้วย Google-approved “G” asset ตาม branding guidelines การเปลี่ยนรูปลักษณ์ต้องไม่เพิ่ม Google client-side SDK หรือเปลี่ยน credential flow โดยไม่มีเหตุผลด้านผลิตภัณฑ์หรือความปลอดภัยแยกต่างหาก
- ปุ่ม Google ใช้ Light treatment เมื่อ Pocka อยู่ในธีมสว่างและ Dark treatment เมื่ออยู่ในธีมมืด การเปลี่ยนธีมต้องไม่เปลี่ยนข้อความ ขนาดเชิงความหมาย หรือความเด่นของปุ่ม
- การสลับธีมบน Marketing Page ต้องอัปเดตทั้งหน้าและ Login Dialog ทันที พร้อมบันทึก preference สำหรับการกลับมาใช้งานครั้งถัดไป
- ฟอร์ม Waitlist เก็บเฉพาะ email และการยินยอมให้ติดต่อเรื่อง Beta พร้อมแจ้งว่าการส่งคำขอไม่ได้ให้สิทธิ์เข้าใช้ทันที
- email ของ Waitlist ต้อง normalize และ unique; การส่งซ้ำตอบผลสำเร็จแบบเป็นกลางและไม่สร้างรายการซ้ำ
- Beta Waitlist แยกจาก Beta Allowlist อย่างชัดเจน การอยู่ใน Waitlist ไม่ให้สิทธิ์สร้างบัญชีหรือเข้าถึงข้อมูล
- รุ่นแรกผู้ดูแลตรวจและอนุมัติผ่าน CLI เมื่ออนุมัติให้เพิ่ม email เข้า Allowlist บันทึกผู้อนุมัติ/เวลา และส่งอีเมลแจ้งพร้อมลิงก์เข้า Pocka
- การส่งอีเมลอนุมัติต้องใช้ durable outbox/job แบบ at-least-once ใช้ Message-ID คงที่ต่อ notification และ retry ได้ตาม ADR-010/011 ความล้มเหลวของ email ต้องไม่ย้อนการอนุมัติ โดยยอมรับว่า SMTP ไม่รับประกัน exactly-once หลัง provider รับข้อความแล้วแต่ process ล้มก่อนบันทึกผล
- ออกแบบสถานะและ audit data ให้รองรับ Admin UI ในอนาคต แต่ Admin UI อยู่นอกขอบเขตรุ่นนี้
- Privacy Notice ต้องระบุวัตถุประสงค์และระยะเวลาเก็บ email ของ Waitlist รวมถึงช่องทางถอนคำขอ ก่อนเปิดรับข้อมูลจริง
- คำขอ `PENDING` และ `DECLINED` เก็บไม่เกิน 180 วัน ส่วนข้อมูล `APPROVED` เก็บตลอดช่วงที่บุคคลนั้นมีสิทธิ์ Beta และลบตามวงจรการลบบัญชี/สิทธิ์ ช่องทางถอนคำขอต้องเป็นข้อมูลติดต่อจริงที่เจ้าของผลิตภัณฑ์ยืนยันก่อน public deployment

## ผลที่ตามมา

- ผู้ใช้ใหม่เข้าใจคุณค่าของ Pocka และมีเส้นทางแสดงความสนใจแทนการพบทางตันจาก Allowlist
- ผู้ใช้เดิมยังเข้าสู่ระบบได้รวดเร็วจาก navigation และ Dialog
- ผู้ใช้แยกแยะได้ว่ากำลังยืนยันตัวตนกับ Google ไม่ใช่ส่งข้อมูลรับรองให้ Pocka โดยตรง แต่ UI จะมี visual system สองชุดที่ต้องจัดสมดุลร่วมกัน
- ระบบต้องเพิ่ม public write endpoint ที่จำกัด payload, validate email, ป้องกัน abuse และไม่เปิดเผยว่า email ใดอยู่ใน Waitlist หรือ Allowlist
- การเปิดรับ Waitlist สร้างภาระด้าน privacy, retention, moderation และ email delivery ที่ต้องจัดการก่อน production
- หน้า Marketing ต้องมี accessibility สำหรับ navigation, Dialog, focus management, form status และ reduced motion เช่นเดียวกับ application UI

## ทางเลือกที่ไม่เลือก

- Split-screen Login: มีพื้นที่อธิบายคุณค่าน้อยและไม่เหมาะกับการรับ Waitlist
- Public registration: ขัดกับข้อจำกัด Private Beta และ capacity ปัจจุบัน
- ส่งคำขอเข้าอีเมลผู้ดูแลโดยตรง: ตรวจคำขอซ้ำ สถานะ และ audit ได้ยากกว่า
- Admin UI ในรุ่นแรก: เพิ่มขอบเขตและความเสี่ยงโดยยังไม่จำเป็นต่อจำนวนผู้ทดสอบช่วงต้น
