# ADR-010: Google Authentication และการแชร์กระเป๋าแบบอ่านอย่างเดียว

## สถานะ

เสนอ

## บริบท

แอปจะย้ายจากข้อมูลที่เก็บเฉพาะใน browser ไปสู่ระบบที่ผู้ใช้เข้าสู่ระบบด้วย Google Account และเข้าถึงข้อมูลของตนเองได้จากหลายอุปกรณ์ นอกจากนี้ เจ้าของกระเป๋าอาจต้องการแชร์ข้อมูลรายรับ รายจ่าย และเงินเก็บให้ครอบครัวหรือบุคคลอื่นดู โดยไม่อนุญาตให้ผู้รับแชร์เปลี่ยนแปลงข้อมูล

ข้อมูลผู้ใช้ กระเป๋า สมาชิกที่ได้รับสิทธิ์ และรายการทางการเงินมีความสัมพันธ์และข้อกำหนดด้านความถูกต้องชัดเจน จึงต้องมีขอบเขตสิทธิ์ที่ตรวจสอบจาก backend ทุกครั้ง

## การตัดสินใจ

- Backend ใช้ Express และ TypeScript
- ใช้ฐานข้อมูล SQL โดยเลือก PostgreSQL เป็นค่าเริ่มต้น
- ใช้ Google OpenID Connect สำหรับยืนยันตัวตน และใช้ค่า `sub` ของ Google เป็นตัวระบุบัญชีจากผู้ให้บริการ ห้ามใช้ email เป็นตัวระบุหลัก
- แยก User ออกจาก Auth Account เพื่อรองรับผู้ให้บริการเข้าสู่ระบบอื่นในอนาคต
- ผู้ใช้ต้องเข้าสู่ระบบก่อนใช้งานข้อมูลการเงินเสมอ รุ่นแรกไม่มี Guest Mode
- Frontend route ที่แสดง Wallet, Transaction, Savings Goal หรือข้อมูลสรุปทั้งหมดต้องเป็น protected route
- ก่อนเข้าสู่ระบบ ผู้ใช้เข้าถึงได้เฉพาะหน้า Login, OAuth callback, หน้ารับคำเชิญที่ยังไม่เปิดเผยข้อมูลการเงิน และหน้าข้อผิดพลาดที่เกี่ยวข้อง
- กระเป๋าทุกใบมี Owner เพียงผู้เดียว
- รุ่นแรกไม่รองรับการโอนความเป็นเจ้าของ Wallet และไม่มี API สำหรับเปลี่ยน Owner
- Owner ของ Wallet คงเดิมตลอดอายุ Wallet จนกว่า Wallet หรือบัญชีเจ้าของจะเข้าสู่กระบวนการลบ
- แบบจำลองฐานข้อมูลรองรับให้ User เป็นเจ้าของ Wallet ได้หลายใบ และเป็น Viewer ของ Wallet หลายใบ
- UI รุ่นแรกสร้างและแสดง Personal Wallet หลักหนึ่งใบต่อ User แต่ schema และ API ต้องไม่ผูกกับสมมติฐานว่าผู้ใช้มีกระเป๋าได้เพียงใบเดียว
- Wallet ที่ผู้อื่นแชร์ให้แสดงแยกจาก Personal Wallet และต้องบอก Owner อย่างชัดเจนเพื่อป้องกันการสับสน
- รุ่นแรกรองรับสกุลเงิน THB เท่านั้น และยังไม่รองรับอัตราแลกเปลี่ยนหรือรายการหลายสกุลเงิน
- รุ่นแรกกำหนด timezone ของทุก Wallet เป็น IANA timezone `Asia/Bangkok`
- Backend ต้องใช้ timezone ของ Wallet ในการคำนวณขอบเขต “วันนี้”, วัน, เดือน และรายงาน ห้ามใช้ timezone ของเครื่อง client เป็น source of truth
- เก็บ timestamp ในฐานข้อมูลเป็น UTC และแปลงเป็นวันท้องถิ่นตาม `Asia/Bangkok` เมื่อ query หรือคำนวณ domain summary
- จำนวนเงินทุกค่าจัดเก็บเป็นจำนวนเต็มหน่วยสตางค์ ห้ามใช้ floating-point สำหรับ persistence หรือการคำนวณทางการเงิน
- API รับและส่งจำนวนเงินในรูปจำนวนเต็มหน่วยสตางค์ ส่วนการแสดงผลเป็นบาทและทศนิยมไม่เกินสองตำแหน่งเป็นหน้าที่ของ presentation layer
- Transaction เก็บ `occurredOn` เป็นวันที่ตาม Wallet Timezone และเป็นค่าบังคับที่ Owner เลือกหรือแก้ไขได้
- Transaction เก็บ `occurredTime` เป็นเวลาท้องถิ่นแบบ nullable; Owner แก้ไขได้แต่ไม่จำเป็นต้องกรอกเมื่อจำเวลาไม่ได้
- `occurredOn` และ `occurredTime` ใช้แสดงและจัดกลุ่มรายงาน ส่วน `createdAt` เป็น UTC timestamp ที่ระบบกำหนดและผู้ใช้แก้ไม่ได้
- Transaction เก็บ `updatedAt` เป็น UTC timestamp ที่ระบบอัปเดตเมื่อข้อมูลถูกแก้ไข
- Viewer เห็นค่า `updatedAt` ของ Transaction ที่ยังมีอยู่ผ่านข้อความ “แก้ไขล่าสุดเมื่อ…” แต่ไม่เห็นประวัติค่าเดิม
- รุ่นแรกไม่เก็บ version history ของรายละเอียด Transaction และไม่แสดงรายการที่ Owner ลบแล้วแก่ Viewer
- เมื่อ `occurredTime` ไม่มีค่า UI ต้องแสดงเฉพาะวันที่ ห้ามแสดงเวลา `00:00` ที่ทำให้เข้าใจว่าเป็นเวลาจริง
- การเรียง Transaction ภายในวันต้องกำหนดให้แน่นอน: รายการที่มีเวลาเรียงตาม `occurredTime` แล้วใช้ `createdAt` และ `id` เป็นตัวตัดสิน; รายการไม่มีเวลาใช้ `createdAt` และ `id` โดย UI ต้องแยกหรือสื่อสารตำแหน่งอย่างสม่ำเสมอ
- Owner เท่านั้นที่เพิ่ม แก้ไข หรือลบ Transaction และแก้ไขการตั้งค่ากระเป๋าได้
- ผู้รับแชร์มีบทบาท Viewer และอ่านข้อมูลทั้งหมดของกระเป๋าที่ได้รับสิทธิ์ได้ รวมถึงรายละเอียด Transaction, จำนวนเงิน, วันที่, หมวดหมู่, Savings Goal และข้อมูลสรุป
- Viewer เห็นข้อมูลเดิมและข้อมูลใหม่ของกระเป๋าตลอดช่วงที่สิทธิ์ยังมีผล การแชร์ไม่ใช่ snapshot ณ เวลาที่เชิญ
- Viewer ไม่มีสิทธิ์ใช้ฟังก์ชัน export หรือดาวน์โหลดข้อมูลของ Wallet ส่วน Owner เท่านั้นที่ export ได้
- Owner ต้องดูรายชื่อ Viewer และถอนสิทธิ์ของแต่ละคนได้
- Viewer ออกจาก Wallet ที่ได้รับการแชร์ได้เองหลังยืนยันหนึ่งครั้ง โดยไม่ต้องรอ Owner
- เมื่อ Viewer ออก ให้ยุติ Wallet Membership ทันที และทุก request ถัดไปต้องถูกปฏิเสธ
- การออกจาก Wallet ไม่กระทบ Wallet หรือข้อมูลของ Owner และต้องส่ง Security Notification แจ้ง Owner
- Owner เห็นเวลาล่าสุดที่ Viewer แต่ละคนเปิด Wallet ได้จาก `lastViewedAt` บน Wallet Membership
- ระบบเก็บเฉพาะการเปิด Wallet ล่าสุด ไม่เก็บประวัติว่า Viewer เปิดหน้าใดหรือดู Transaction รายการใด
- การอัปเดต `lastViewedAt` ต้อง throttle หรือ coalesce เพื่อลด write ที่เกิดจากทุก API request และห้ามใช้เป็นหลักฐานรับรองว่าผู้ใช้ได้อ่านข้อมูลจริง
- Owner เชิญ Viewer ด้วย email และผู้รับต้องเข้าสู่ระบบด้วย Google Account ที่มี email ตรงกับคำเชิญ
- ก่อนยอมรับคำเชิญ ระบบใช้ email เพื่อยืนยันผู้รับที่ตั้งใจเชิญ เมื่อยอมรับแล้ว Wallet Membership ต้องผูกกับ `userId` ไม่ตรวจสิทธิ์จาก email ในแต่ละ request
- คำเชิญต้องมี token แบบสุ่มที่ใช้ได้ครั้งเดียว โดยฐานข้อมูลเก็บเฉพาะ hash ของ token
- คำเชิญหมดอายุ 7 วันหลังสร้าง และ Owner ยกเลิกคำเชิญที่ยังไม่ถูกตอบรับได้
- เมื่อคำเชิญหมดอายุ ถูกยกเลิก หรือถูกรับแล้ว token เดิมต้องใช้สร้าง Membership ไม่ได้อีก
- ผู้รับต้องยืนยันการยอมรับคำเชิญก่อนสร้าง Wallet Membership ห้ามให้สิทธิ์อัตโนมัติทันทีที่ Owner กรอก email
- Backend ต้องตรวจ authorization จากสมาชิกและบทบาทของกระเป๋าในทุก request ห้ามพึ่งการซ่อนปุ่มใน frontend
- ใช้ server-side session ผ่าน cookie ที่เป็น `HttpOnly`, `Secure` ใน production และกำหนด `SameSite` ให้เหมาะกับ topology ของ frontend/backend
- Session ใช้ rolling inactivity timeout 7 วัน โดยเลื่อนวันหมดอายุเมื่อผู้ใช้ใช้งานและ session ยังถูกต้อง
- ไม่แสดง popup เตือนก่อน Session หมดอายุ 24 ชั่วโมง เพราะ Session ที่มีการใช้งานจะถูกต่ออายุอยู่แล้ว
- เมื่อ Session หมดอายุจริง ให้พาไปหน้า Login พร้อมข้อความอธิบาย และเก็บ safe return path เพื่อกลับสู่หน้าเดิมหลังเข้าสู่ระบบ ห้ามเก็บ URL ภายนอกเป็น return path
- ผู้ใช้ดูและออกจากระบบรายอุปกรณ์ได้ รวมถึงมีคำสั่ง “ออกจากระบบทุกอุปกรณ์” เพื่อเพิกถอน Session ทั้งหมดของตน
- การออกจากระบบต้องเพิกถอน Session ฝั่ง backend และลบ session cookie ห้ามทำเพียงเปลี่ยน route ฝั่ง frontend
- บน desktop ผู้ใช้เปิด Account Menu ได้จากส่วนโปรไฟล์ชื่อผู้ใช้มุมล่างซ้าย ส่วนบน mobile ใช้ปุ่ม avatar แยกที่มุมขวาบนของหน้า ไม่รวมไว้กับเมนูตั้งค่า
- Account Menu แสดงชื่อที่ใช้แสดง, email, ป้าย “บัญชีส่วนตัว” และคำสั่งออกจากระบบ โดยปิดได้เมื่อคลิกภายนอกหรือกด `Escape` และต้องรองรับ keyboard navigation, focus management และ screen reader
- User เก็บ `avatarUrl` แบบ nullable จาก claim `picture` ของ Google และอัปเดตค่าใหม่ทุกครั้งที่เข้าสู่ระบบด้วย Google โดยเก็บเฉพาะ URL ไม่ดาวน์โหลดไฟล์รูปมาไว้ในระบบ
- Profile Avatar ต้องแสดงรูปจาก `avatarUrl` ก่อนเสมอในส่วนโปรไฟล์มุมล่างซ้ายบน desktop, ปุ่ม avatar มุมขวาบนบน mobile และส่วนข้อมูลผู้ใช้ใน Account Menu โดย browser โหลดรูปจาก Google โดยตรง
- รูป Profile Avatar แสดงเป็นวงกลม ครอบจากกึ่งกลางด้วย `object-fit: cover` และไม่บีบสัดส่วน หากไม่มี `avatarUrl` หรือรูปโหลดไม่สำเร็จ ต้อง fallback เป็นอักษรตัวแรกของชื่อทันทีโดยไม่แสดง broken-image icon
- คำสั่งออกจากระบบจาก Account Menu หมายถึง Current-Session Logout เท่านั้น: ต้องแสดงหน้าต่างยืนยันที่มี “ยกเลิก” และ “ออกจากระบบ” โดย focus เริ่มที่ “ยกเลิก” และผู้ใช้ยกเลิกได้ด้วย `Escape` หรือ backdrop
- ระหว่างส่งคำขอออกจากระบบ ต้องป้องกันการส่งซ้ำและห้ามปิดหน้าต่างยืนยัน หากสำเร็จให้ไปหน้า Login พร้อมข้อความ “ออกจากระบบแล้ว”
- หากออกจากระบบไม่สำเร็จ ต้องคง Session และหน้า dashboard ไว้ ไม่ล้างสถานะ authentication ฝั่ง frontend คงหน้าต่างยืนยันไว้ แสดงข้อความ “ออกจากระบบไม่สำเร็จ กรุณาลองอีกครั้ง” และให้ลองใหม่ได้
- ไม่เก็บ Google access token หรือ refresh token หากแอปต้องการเพียงข้อมูลระบุตัวตนพื้นฐาน
- ผู้ใช้ลบบัญชีของตนได้ แต่ต้องผ่านหน้าต่างยืนยันที่อธิบายผลกระทบก่อนดำเนินการ
- การลบบัญชีต้องจัดการ Wallet ที่เป็นเจ้าของ, Membership ที่เป็น Viewer, คำเชิญ และ Session ทั้งหมดอย่างสอดคล้องกัน
- หลังยืนยันลบ ให้เข้าสู่สถานะ pending deletion เป็นเวลา 30 วันก่อนลบถาวร
- เมื่อเริ่ม pending deletion ต้องเพิกถอน Session ทั้งหมด ยกเลิกคำเชิญ ปิดการแชร์ Wallet ที่เป็นเจ้าของ และหยุดการเข้าถึงข้อมูลทันที
- Viewer ต้องมองไม่เห็น Wallet ของบัญชีที่ pending deletion ตั้งแต่วินาทีที่เริ่ม workflow ไม่ต้องรอครบ 30 วัน
- ภายใน 30 วัน เจ้าของใช้ Google Account เดิมเข้าสู่ recovery flow เพื่อยกเลิกการลบและเปิดใช้บัญชีอีกครั้งได้ โดยยังห้ามเข้าหน้าข้อมูลจนกู้คืนสำเร็จ
- เมื่อครบ 30 วัน ให้ลบบัญชี Wallet ที่เป็นเจ้าของ ข้อมูลการเงิน และความสัมพันธ์ที่เกี่ยวข้องอย่างถาวร

### การแจ้งเตือนทางอีเมล

- ส่งอีเมลถึงผู้รับเมื่อ Owner สร้าง Wallet Invitation โดยลิงก์คำเชิญต้องใช้ token แบบใช้ครั้งเดียว
- ส่งอีเมลถึง Owner เมื่อผู้รับยอมรับคำเชิญ
- ส่งอีเมลถึง Owner เมื่อ Viewer ออกจาก Wallet ที่แชร์
- ส่งอีเมลถึง Viewer เมื่อ Owner ถอนสิทธิ์ และส่งผลยืนยันว่าสำเร็จให้ Owner
- ส่งอีเมลถึงเจ้าของเมื่อเริ่ม Account Deletion และเมื่อบัญชีถูกกู้คืน
- ไม่ส่งอีเมลทุกครั้งที่ Login ปกติ เพื่อลดการแจ้งเตือนที่ไม่จำเป็น
- ห้ามใส่ยอดเงิน รายการ Transaction หรือรายละเอียดการเงินอื่นใน subject หรือเนื้อหาอีเมล
- การส่งอีเมลต้องเกิดผ่านงานเบื้องหลังหรือ outbox ที่ retry ได้ และความล้มเหลวของ email ต้องไม่ย้อน transaction หลักที่สำเร็จแล้ว

### การจับภาพหน้าจอ

- รุ่นแรกยังคงเป็น React Web/PWA และไม่เพิ่ม native app หรือ Android wrapper เพียงเพื่อบล็อก screenshot
- React Web/PWA ไม่สามารถป้องกัน screenshot ของระบบปฏิบัติการได้อย่างน่าเชื่อถือ จึงห้ามอ้างว่า Viewer แคปหน้าจอไม่ได้
- แม้ปิดการ export แล้ว ผู้รับยังสามารถคัดลอกข้อมูลด้วย screenshot, กล้องอีกเครื่อง หรือการจดบันทึกได้ การแชร์จึงต้องอาศัยความไว้วางใจและคำเตือนก่อนยืนยัน
- หากมี Android native app ในอนาคต ให้ใช้ secure window เช่น `FLAG_SECURE` กับหน้าข้อมูลการเงินเป็น defense in depth
- บน iOS สามารถตอบสนองต่อสถานะ screen recording หรือ mirroring และรับ notification หลัง screenshot ได้ แต่ไม่ถือว่าเป็นการป้องกัน screenshot ที่สมบูรณ์
- สำหรับ Web รุ่นแรก ให้ซ่อนข้อมูลเมื่อ app ไป background เท่าที่ lifecycle อนุญาต และแสดง watermark ที่ระบุผู้รับแชร์เพื่อยับยั้งการเผยแพร่ โดยต้องไม่อ้างว่าเป็นมาตรการป้องกันเด็ดขาด

### การนำเข้าข้อมูลจากอุปกรณ์

- หลังเข้าสู่ระบบครั้งแรก หากพบ Transaction หรือ Savings Goal ใน `localStorage` ให้แสดงหน้าต่างถามก่อนส่งข้อมูลไป backend
- หน้าต่างต้องสรุปชนิดและจำนวนข้อมูลที่จะนำเข้า และให้เลือก “นำเข้าข้อมูลในอุปกรณ์นี้” หรือ “เริ่มใหม่” อย่างชัดเจน
- ห้ามนำเข้าข้อมูลอัตโนมัติเพียงเพราะผู้ใช้เข้าสู่ระบบสำเร็จ
- การนำเข้าต้องใช้ operation identifier หรือกลไก idempotency เพื่อไม่ให้การ retry สร้างรายการซ้ำ
- ข้อมูลปลายทางต้องอยู่ใน Personal Wallet ของผู้ใช้ที่กำลังเข้าสู่ระบบเท่านั้น
- ห้ามลบข้อมูลใน `localStorage` จนกว่า backend จะยืนยันว่าการนำเข้าสำเร็จครบถ้วน
- หลัง backend ยืนยันความสำเร็จ ให้ลบ Transaction และ Savings Goal เดิมออกจาก `localStorage` โดยอัตโนมัติ
- หลังลบ ให้เก็บเฉพาะ marker ที่ไม่มีข้อมูลการเงินเพื่อระบุว่าอุปกรณ์นี้นำเข้าแล้ว และไม่แสดงคำถามนำเข้าซ้ำ
- หากล้างข้อมูลในเครื่องไม่สำเร็จ ต้องแจ้งผู้ใช้และให้ลองล้างอีกครั้ง โดยห้าม retry การส่งข้อมูลขึ้น backend จนเกิดข้อมูลซ้ำ

## แบบจำลองโดเมน

- **User:** บุคคลภายในระบบ
- **Auth Account:** ตัวเชื่อม User กับบัญชีจากผู้ให้บริการ โดยมี `provider` และ `providerSubject`
- **Wallet:** ขอบเขตข้อมูลทางการเงินที่มี Owner หนึ่งคน
- **Personal Wallet:** Wallet หลักที่ระบบสร้างให้ User และเป็นกระเป๋าหลักเพียงใบเดียวที่ UI รุ่นแรกให้จัดการ
- **Wallet Ownership:** ความสัมพันธ์ถาวรในรุ่นแรกระหว่าง Wallet กับ Owner หนึ่งคน ซึ่งไม่สามารถโอนไปยัง User อื่นได้
- **Money Amount:** จำนวนเต็มหน่วยสตางค์ในสกุล THB ซึ่งใช้เป็นค่ามาตรฐานใน database, API และ domain calculation
- **Wallet Timezone:** IANA timezone `Asia/Bangkok` ที่ backend ใช้กำหนดขอบเขตวันและเดือนร่วมกันสำหรับ Owner และ Viewer
- **Occurred On:** วันที่ท้องถิ่นที่ Transaction เกิดขึ้นจริง เป็นค่าบังคับและแก้ไขได้
- **Occurred Time:** เวลาท้องถิ่นที่ Transaction เกิดขึ้นจริง เป็นค่าทางเลือกและแก้ไขได้
- **Created At:** UTC timestamp ที่ระบบสร้างเมื่อบันทึก Transaction และผู้ใช้แก้ไม่ได้
- **Updated At:** UTC timestamp ที่ระบบเปลี่ยนเมื่อแก้ไข Transaction
- **Transaction Edit Indicator:** ข้อความบอกเวลาแก้ไขล่าสุดจาก `updatedAt` โดยไม่เปิดเผยค่าเดิมหรือสร้าง version history
- **Wallet Membership:** ความสัมพันธ์ระหว่าง User กับ Wallet พร้อมบทบาท `owner` หรือ `viewer`
- **Last Viewed At:** เวลาล่าสุดโดยประมาณที่ Viewer เปิด Wallet ซึ่ง Owner ใช้ตรวจการเข้าถึงระดับสูงได้
- **Leave Shared Wallet:** workflow ที่ Viewer ยืนยันเพื่อยุติ Membership ของตนและหยุดการเข้าถึง Wallet ทันที
- **Wallet Invitation:** คำเชิญแบบใช้ครั้งเดียวที่ระบุ Wallet, email ผู้รับ, ผู้เชิญ, วันหมดอายุ 7 วัน และสถานะการตอบรับ
- **Read-only Share:** สิทธิ์ที่ให้ Viewer อ่านรายละเอียดทั้งหมดของ Wallet ที่เปลี่ยนแปลงตามข้อมูลล่าสุด โดยไม่สร้าง แก้ไข หรือลบข้อมูล
- **Transaction:** รายการทางการเงินที่สังกัด Wallet ไม่ผูกกับ User โดยตรง
- **Session:** สถานะการเข้าสู่ระบบที่ backend ตรวจสอบและเพิกถอนได้
- **Rolling Session Expiry:** การเลื่อนวันหมดอายุของ Session เมื่อมีการใช้งาน โดย Session จะหมดอายุเมื่อไม่มีการใช้งานต่อเนื่อง 7 วัน
- **Screen-capture Deterrence:** มาตรการลดแรงจูงใจหรือโอกาสการจับภาพ เช่น secure window หรือ watermark ซึ่งไม่รับประกันว่าจะหยุดการทำสำเนาได้ทุกวิธี
- **Account Deletion:** workflow ที่ผู้ใช้ยืนยันเพื่อลบบัญชีและจัดการข้อมูล ความสัมพันธ์ และ Session ที่เกี่ยวข้องทั้งหมด
- **Pending Deletion:** ช่วงเวลา 30 วันที่บัญชีและการแชร์ถูกปิดใช้งาน แต่เจ้าของยังยกเลิกการลบได้ก่อนลบข้อมูลถาวร
- **Security Notification:** อีเมลที่แจ้งการเปลี่ยนสิทธิ์หรือสถานะบัญชีโดยไม่เปิดเผยรายละเอียดการเงิน
- **Device Data Import:** การย้ายข้อมูลเดิมจาก `localStorage` ไปยัง Personal Wallet หลังผู้ใช้ให้ความยินยอมอย่างชัดเจน

## ผลกระทบ

- Transaction และ Savings Goal เดิมต้องย้ายจากการเป็นข้อมูลระดับ browser ไปสังกัด Wallet
- การรองรับหลาย Wallet ใน schema ทำให้ทุก query และ unique constraint ที่เกี่ยวกับข้อมูลการเงินต้องมี `walletId`
- การเพิ่ม ownership transfer ในอนาคตต้องมี ADR ใหม่ ครอบคลุมการยืนยันผู้รับ ผลต่อ Viewer และ Account Deletion
- การรองรับสกุลเงินอื่นหรือหลายสกุลเงินต้องมี ADR ใหม่และห้ามรวมยอดข้ามสกุลโดยไม่มีนโยบายอัตราแลกเปลี่ยน
- การเปลี่ยนหรือรองรับหลาย timezone ต้องมีนโยบายต่อ Transaction และรายงานย้อนหลัง จึงไม่อยู่ในขอบเขตรุ่นแรก
- Storage และ domain เดิมที่ใช้ `createdAt` เป็นวันเกิดรายการต้องย้ายไปใช้ `occurredOn` และ `occurredTime` โดยคง `createdAt` สำหรับ metadata และ deterministic ordering เท่านั้น
- การไม่มี Transaction version history ลดข้อมูลอ่อนไหวที่ต้องเก็บ แต่หมายความว่าจะตรวจย้อนหลังหรือกู้ค่าก่อนแก้ไขไม่ได้
- ต้องเก็บสถานะหรือ identifier ของการนำเข้าเพื่อป้องกันข้อมูลซ้ำเมื่อ network ล้มเหลวหรือผู้ใช้ retry
- หลังนำเข้าสำเร็จ browser จะไม่เป็น persistence หลักของข้อมูลการเงินอีกต่อไป และ UI ต้องอ่านข้อมูลจาก backend
- `localStorage` เดิมใช้เฉพาะการตรวจหาและนำเข้าข้อมูลครั้งแรก ห้ามใช้เป็นช่องทางสร้างหรือใช้งานข้อมูลแบบ Guest ต่อไป
- API อ่านข้อมูลต้องรองรับทั้ง Owner และ Viewer ส่วน API ที่เปลี่ยนข้อมูลต้องอนุญาตเฉพาะ Owner
- ข้อมูลการเงินทั้งหมดของ Wallet เป็นข้อมูลที่ Viewer อ่านได้ จึงต้องแสดงคำเตือนและขอการยืนยันจาก Owner ก่อนแชร์
- การถอนสิทธิ์หยุดการเข้าถึงในอนาคต แต่ไม่สามารถเรียกคืน screenshot หรือสำเนาที่ Viewer บันทึกไว้นอกระบบได้
- ต้องกำหนดวิธีส่ง email ก่อน implement
- PostgreSQL เหมาะกับ foreign keys, unique constraints, transactions และการสรุปข้อมูลทางการเงิน
- เมื่อ implement ต้องเพิ่ม Prettier และให้คำสั่งตรวจสอบรวม formatting เป็นส่วนหนึ่งของ Definition of Done
- กระบวนการลบถาวรต้อง retry ได้อย่างปลอดภัยและมีงานเบื้องหลังที่ตรวจสอบบัญชีซึ่งครบกำหนด 30 วัน
- ต้องเลือกผู้ให้บริการส่ง transactional email และกำหนด outbox/worker ก่อน implement การเชิญ
- `lastViewedAt` เป็นข้อมูลประกอบด้านความปลอดภัย ไม่ใช่ audit trail แบบละเอียดหรือหลักฐานการอ่าน
